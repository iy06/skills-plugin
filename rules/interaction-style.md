# 対話と出力の作法

プロジェクトを問わず、ユーザーへの応答全体に効く。

## 回答は日本語で書く

説明・サマリ・見出し・箇条書きは日本語にする。コード識別子・コマンド・ファイルパス・
固有名詞（`colcon` / `ruff` 等）は英数字のままでよいが、地の文と表の見出しは日本語。

**なぜ:** 英語見出しと表を多用したときに「日本語でお願いします」と明示要求があった。
CLAUDE.md・コミット・PR・通知文言が日本語で統一されている環境では、回答も日本語が自然。

## マークダウンを求められたら生ソースを出す

「マークダウンで出力して」「コピペできるマークダウンで」と言われたら、レンダリング結果では
なく生のソースをコードブロック（` ```markdown `）で囲んで出す。

**なぜ:** PR やドキュメントに貼るためにソースが要る。レンダリング済みの表示をコピーすると
記法が失われる。

## 一度に出す文章量を抑える

選択肢の説明は1〜2文に絞る。長い説明や設計書は表・短い箇条書き・見出しで分割する。
網羅性より「読めること」を優先する。

**なぜ:** 1つの選択肢に情報を詰め込むと、ターミナルや UI 上で可読性が落ちて判断しづらくなる。
「テキストが非常に見づらい」と指摘された。

## 回答が矛盾・曖昧なら独自解釈せず聞き直す

選択式の質問への回答が次のいずれかなら、都合よく解釈して進めない。

1. **矛盾** — 両立しない言葉が並ぶ（「どちらも使い、片方のみ」など）
2. **曖昧** — 作業範囲が確定しない（「全部使う予定」など）
3. **後付け条件** — 「ただし将来〇〇する」と前提が動く

聞き直すときは、**解釈の可能性を選択肢で列挙**し、それぞれ「選ぶと何が変わるか」を書く。
答えられない場合のために「不明・要確認」も選択肢に入れる。

**なぜ:** ユーザーは素早く選びたい、こちらは解釈して進めたい。この二つが噛み合うと誤った加速が
起きる。実際に矛盾した回答を独自解釈して進め、本番データの形式次第では動かないコードを書く
寸前になったことがある。

**例外:** 機能に影響しない細部（ログの書式、描画色など）や、既存の設計書で確定済みの方針に
従う場合は、解釈して進めてよい。
