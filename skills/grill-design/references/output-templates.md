# grill-design 出力ファイルの雛形

Step 6 で書き出す 3 ファイルの中身と書き方のルール。本体の Step 6-3 から参照される。

## 1. ファイル 1：`docs/design-foundation.md`（人が読む設計書）

「なぜそうするか」を残すファイル。トークンの **値** はここに書かず、`design-tokens.json` を正本として参照する（値が 2 箇所にあると必ずずれるため）。トークンの節では、名前・用途・根拠だけを書く。

```markdown
# <アプリ名> UI 設計基盤（Design Foundation）

> 値の正本：`design-tokens.json` ／ 実装ルール：`.claude/rules/design.md`

## 1. ユーザーと利用シーン
## 2. 採用セオリー
（レイヤー / セオリー / 採用度 / このアプリでの作用）
## 3. デザイン原則
（5〜7 個。各原則に 優先するもの・抑えるもの / 根拠 / Do / Don't）
## 4. デザインシステム
### 4.1 トークン
（トークン名 / 用途 / 根拠となる原則・セオリー。値は design-tokens.json を参照）
### 4.2 コンポーネント仕様
### 4.3 使用禁止事項
### 4.4 トレーサビリティ表
## 5. レイアウト
### 5.1 共通レイアウト
### 5.2 画面テンプレート
## 6. 検証方法
## 7. 未確定事項・今後の検討
## 付録：用語の整理（セオリー / 原則 / デザインシステム / ビジュアルスタイル）
```

## 2. ファイル 2：`design-tokens.json`（機械が読む値）

W3C Design Tokens Community Group（DTCG）形式で書く。Figma の Variables やコード（CSS 変数、Tailwind 設定、Style Dictionary など）に変換しやすい。

書き方のルール：

- 各トークンは `$value` と `$type` を持つ。`$type` はグループに書けば配下に引き継がれる
- 意味トークンは `{color.red.600}` のような参照で基本トークンを指す
- 意味トークンの `$description` に **用途と根拠（原則番号）** を書く。これがコードやレビューで「なぜこの色か」を辿る手がかりになる
- WCAG を採用した場合は、文字色 × 背景色の組み合わせのコントラスト比を書き出し前に計算して確認し、基準を満たさない組み合わせがあればユーザーに報告する（計算は実際にスクリプトで行う。目視で判断しない）

構成例（値はプロダクトごとに決める）：

```json
{
  "color": {
    "$type": "color",
    "red": { "600": { "$value": "#D92D20" } },
    "gray": { "50": { "$value": "#F9FAFB" }, "900": { "$value": "#111827" } },
    "status": {
      "danger": {
        "$value": "{color.red.600}",
        "$description": "異常・エラー・破壊的操作のみに使用。装飾・ブランド表現には使わない（原則2・前注意属性）"
      }
    },
    "text": {
      "primary": { "$value": "{color.gray.900}", "$description": "本文。背景 surface.default に対し 4.5:1 以上（WCAG AA）" }
    }
  },
  "space": {
    "$type": "dimension",
    "1": { "$value": "4px" },
    "2": { "$value": "8px" },
    "inset": {
      "component": { "$value": "{space.2}", "$description": "コンポーネント内の余白。要素間より必ず小さくする（近接の原則）" }
    }
  },
  "font": {
    "size": { "$type": "dimension", "body": { "$value": "14px" } },
    "family": { "$type": "fontFamily", "base": { "$value": ["Inter", "Noto Sans JP", "sans-serif"] } }
  },
  "duration": {
    "$type": "duration",
    "fast": { "$value": "150ms", "$description": "状態変化のフィードバック（ドハティの閾値）" }
  }
}
```

含めるグループ：`color`（基本・意味・データ可視化）、`space`、`font`（family / size / weight / lineHeight）、`size`（クリック領域の最小値、行の高さ）、`radius`、`shadow`、`duration` / `easing`。Step 4 で決めなかったグループは作らない。

## 3. ファイル 3：`.claude/rules/design.md`（実装とレビューで守らせるルール）

Claude Code は `.claude/rules/` のファイルを自動で読み込み、`pr-review` スキルもこのディレクトリのルールでレビューする。**判定できる形で、短く、命令形で** 書く。理由は 1 行だけ添え、詳しくは設計書を参照させる。

書き方のルール：

- 各ルールに ID（`DS-01` など）を振る。レビューコメントで「DS-03 違反」と指せるようにするため
- 各ルールの末尾に根拠の原則番号を書く
- 「気をつける」「なるべく」のような判定できない表現は使わない
- 感覚的な原則（「情報密度を優先する」など）は、判定できる形に言い換えてから載せる。言い換えられないものは設計書にだけ残す
- UI ファイルにだけ適用したい場合は、先頭の `paths` にスタイルとコンポーネントのファイルパターンを書く（プロジェクトの構成に合わせる）

テンプレート：

```markdown
---
paths:
  - "src/**/*.{tsx,jsx,vue,svelte,css,scss}"
---

# デザインルール

UI を実装・変更するときは次のルールに従う。判断に迷ったら `docs/design-foundation.md` のデザイン原則を参照し、値は `design-tokens.json` の意味トークンだけを使う。

## デザイン原則（要約）
1. <原則1を1行で>
2. ...

## 必須ルール（MUST）
- DS-01: 色・余白・文字サイズ・角丸・影は意味トークン経由で指定する。カラーコードや px 値を直接書かない（原則3）
- DS-02: 状態（成功・警告・エラー）を色だけで表さず、アイコンかテキストを併用する（WCAG 1.4.1）
- DS-03: 1 画面に primary ボタンは 1 つだけ置く（原則1・フォン・レストルフ効果）
- DS-04: データを表示するコンポーネントは、読み込み中・空・エラーの 3 状態を実装する（原則5）

## 禁止事項（MUST NOT）
- DS-10: `color.status.*` を装飾やブランド表現に使わない（原則2）
- DS-11: グラフに 3D 表現・影・グラデーションを使わない（Data-ink 比）

## レビュー観点
- 新しいトークンやコンポーネントが追加されていたら、設計書への追記が必要か確認する
- ルールに当てはまらない新しい判断が含まれていたら、設計書の原則に照らして妥当かを指摘する
```
