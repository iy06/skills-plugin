# grill-design

Webアプリの UI 設計の土台を、上流から順に質問駆動で固めるためのスキル。セオリーの作用を解説しながら「どれを・どの強さで採用するか」をユーザーと一緒に決め、そこからデザイン原則 → デザインシステムのルール → レイアウトへと落としていく。

## このスキルの位置づけ

```
grill-product（何を作るか・要件定義書）… アプリで 1 回
  → grill-design ← 本スキル（どう見せ、どう使わせるか・UI 設計の土台）… アプリで 1 回
  → grill-screen（どんな画面を、どう遷移させるか・画面設計書）… 機能ごとに繰り返す ※作成予定
  → grill-me（どう実装するか・技術設計書）→ 実装
```

`grill-product` の要件定義書があれば、それを入力として使う。本スキルが出力する 3 つのファイルは、`grill-screen` での画面設計、Figma やコードでのビジュアル化、実装とレビューのすべてで参照される。

本スキルで決めるのは **アプリ全体に共通する土台** まで。「顧客一覧から顧客詳細へ遷移する」といった具体的な画面や遷移は要件に依存するため、`grill-screen` で決める。

`grill-screen` はまだ作成していない。それまでは、画面一覧・遷移は `grill-me` で技術設計と合わせて決める。本文中で `grill-screen` に回すと書いてある箇所は、`grill-screen` が無ければ `grill-me` に読み替える。

## このスキルの目的

「デザインシステムとレイアウトを作り込めば良い UI になる」わけではない。デザインシステムは一貫性を保証するが、使いやすさは保証しない。使いやすさを決めるのは、その手前にある **「なぜその配置・色・余白にするのか」という判断基準** である。

本スキルでは、その判断基準を次の 5 段で作る。

1. **ユーザーと利用シーン**を決める（誰が・どのくらいの頻度で・何を判断/操作するために使うか）
2. **レイヤーごとにセオリーを選ぶ**（作用を理解したうえで、採用の強さを決める）
3. **セオリー同士の衝突に優先順位を付け、デザイン原則として 5〜7 個に言語化する**
4. **原則をデザインシステムのルールに落とす**（トークン・コンポーネント仕様・禁止事項）
5. **レイアウトを組む**（画面テンプレートと検証方法）

最終的に、役割の違う 3 つのファイルを出力する。

| ファイル | 中身 | 誰がいつ使うか |
|---|---|---|
| `docs/design-foundation.md` | 原則・判断の理由・画面テンプレートの型 | 人（と Claude）が画面を設計するとき、迷ったときに参照する |
| `design-tokens.json` | 色・余白・文字などの値（W3C Design Tokens 形式） | Figma やコードが直接読み込む。**値の正本** |
| `.claude/rules/design.md` | 守るべきルールと禁止事項 | Claude Code が実装するとき、`pr-review` がレビューするときに自動で参照する |

ユーザーはセオリーに詳しいとは限らない。**Claude は各セオリーが「何に作用し、採用すると何を守らなければならないか」を解説しながら進める**。ゴールは、ユーザーが自分の言葉で「うちはこの理由でこう判断する」と説明できる状態にすること。

## 用語の整理（ユーザーが混乱したら最初に説明する）

| 用語 | 何か | 誰のものか | 例 |
|---|---|---|---|
| **UIセオリー** | 人の知覚・認知・行動についての法則や、確立された設計指針 | 人類共通。プロダクトに依存しない | 「選択肢が多いほど判断が遅くなる」（ヒックの法則） |
| **デザイン原則** | セオリーを材料に、自分たちのユーザーと目的に合わせて「こう判断する」と決めたルール | そのプロダクト固有 | 「1画面で主要アクションは1つ。その他は二次ボタンに下げる」 |
| **デザインシステム** | 原則を具体的な値と部品にしたもの | そのプロダクト固有 | 色・余白・文字のトークン、ボタンやカードのコンポーネント |
| **ビジュアルスタイル** | ブランドの印象を作る見た目の選択 | そのプロダクト固有 | ブランドカラー、角丸の大きさ、フォントの雰囲気 |

重要な区別：

- **セオリーは見た目の好みで選ぶものではない**。「伝わるか・使えるか」に作用するので、ユーザーのタスクで判断する。
- **好みで決めてよいのはビジュアルスタイル**。ただしセオリー（特に L1・L5）の制約の内側で決める。
- **デザイン原則はセオリーの引用ではない**。セオリー同士がぶつかる箇所で、どちらを優先するかを決めた「判断」が原則になる。

## 全体フロー

0. **起動と下調べ**（要件定義書・既存コード・既存スタイルの確認）
1. **ユーザーと利用シーンの確定**
2. **セオリーの選定**（レイヤーごとに解説 → 採用度の決定）
3. **デザイン原則の策定**（衝突の解決 → 5〜7 個に言語化）
4. **デザインシステムへの落とし込み**
5. **レイアウトと検証方法**
6. **3 つのファイルの出力**（設計書・トークン・ルール）
7. **次のステップの選択**（コード化 / Figma 化 / 画面設計・技術設計）

各ステップの終わりに、そのステップで決まったことを短く見せて合意を取ってから次へ進む。

## Step 0: 起動と下調べ

`/grill-design` だけで呼ばれたら「どのアプリの UI 設計を固めますか？」と聞く。対象が添えられていれば飛ばす。

次に、**聞かなくても分かることを先に調べる**（grill 系共通の原則）。

- `grill-product` の要件定義書や README、docs があれば読む（ターゲットユーザー・ユースケースが書いてあれば Step 1 がほぼ埋まる）
- 既存コードがあれば、スタイルの現状を把握する
  - CSS 変数 / Tailwind の設定 / テーマファイル（色・余白・フォントの定義）
  - UI ライブラリ（MUI、shadcn/ui、Ant Design、Chakra など）の有無
  - 既存コンポーネントの構成、画面の種類（一覧・詳細・フォーム・ダッシュボードなど）
- 調べた結果を「分かったこと」と「聞く必要があること」に分け、分かったことは「コードからはこう見えました。合っていますか？」と確認するだけにする

## Step 1: ユーザーと利用シーンの確定

以降のすべての判断の軸になる。ここが曖昧だとセオリーの優先順位が決まらないので、粘る価値がある。

推奨回答を添えながら、次を確認する（関連するものはまとめて聞いてよい）。

1. **主なユーザーは誰か**（職種・IT リテラシー・専門知識の有無）
2. **利用頻度と時間**（毎日数時間 / 毎日数分 / 週・月に数回 / 初回のみ）
3. **主なタスク**（何を判断するか・何を操作するか。上位 3 つ）
4. **利用環境**（デスクトップ中心か、モバイルもあるか、画面サイズ、屋外や騒がしい場所か）
5. **失敗したときのコスト**（誤操作で何が起きるか。取り消せるか）
6. **アクセシビリティの要求**（公共性・社外ユーザー・法令や社内規定の有無）

回答から、**アプリの型**を判定してユーザーに確認する。型は Step 2・3 の推奨を決める主要な材料になる。

| 型 | 特徴 | 典型的な画面 |
|---|---|---|
| A. 業務オペレーション型 | 同じ人が毎日長時間使う。熟練する | 一覧・詳細・入力フォーム・管理画面 |
| B. モニタリング型 | 異常の早期発見が目的。常時表示されることも | 監視ダッシュボード、アラート一覧 |
| C. 意思決定・レポート型 | たまに見て判断する。要約が重要 | 経営 KPI ダッシュボード、レポート |
| D. 探索・分析型 | 仮説を立てて掘り下げる | フィルター・ドリルダウン・比較画面 |
| E. 一般ユーザー向けサービス型 | 初見・低頻度の利用者が多い。離脱されやすい | 登録フロー、設定、マイページ |
| F. 集客・訴求型 | 読ませて行動させる | LP、紹介ページ、料金ページ |

1 つのアプリに複数の型が混ざることは多い（例：管理画面は A、トップのダッシュボードは C）。その場合は **画面群ごとに型を割り当てる**。

Step 1 の合意内容を次の形で見せてから Step 2 へ進む。

```markdown
### ユーザーと利用シーン
- 主なユーザー：
- 利用頻度：
- 主なタスク（上位3つ）：
- 利用環境：
- 失敗のコスト：
- アクセシビリティ要求：
- アプリの型：（画面群ごとに）
```

## Step 2: セオリーの選定

このスキルの中核。**ユーザーはセオリーの作用を知らない前提で進める。**

### 進め方

1. まず、セオリーには 5 つのレイヤーがあり、**レイヤーによって「選ぶ」性質が違う**ことを説明する
   - L1（知覚・認知）と L5（規格）は **原則すべて守る**。選ぶのは「どこまで厳密にやるか」
   - L2（ユーザビリティ原則）・L3（視線とレイアウト）・L4（情報設計と可視化）は **型によって強弱を付ける**
2. **1 レイヤーずつ**、後述の「セオリーカタログ」を使って解説する。一度に全レイヤーを出さない
   - 各セオリーについて「何に作用するか」「採用すると何を守る必要があるか」を、Step 1 のアプリに当てはめた具体例で説明する
   - 抽象論ではなく「あなたのアプリの〇〇画面ではこうなる」と言う
3. レイヤーごとに、各セオリーの **採用度** を推奨付きで提示し、ユーザーに決めてもらう
   - **必須**：常に守る。破る場合は明示的な理由が必要
   - **重視**：このアプリで特に強く効かせる。原則の根拠になる
   - **標準**：一般的な範囲で守る
   - **対象外**：このアプリでは効かせない（理由を書く）
4. 全レイヤーが終わったら、採用セオリー一覧を表で見せて合意を取る

ユーザーが「よく分からない」と言ったら、そのセオリーを **守った場合 / 破った場合** の具体的な画面の違いを文章で描写して比べる。それでも決まらなければ Claude の推奨で進め、設計書の「未確定事項」に残す。

### セオリーカタログ

Claude はこのカタログを解説の材料として使う。各項目の「DS への反映例」は Step 4 で再利用する。

#### L1: 知覚・認知（人間の仕様。原則すべて「必須」）

| セオリー | 何に作用するか | 採用すると守ること | DS への反映例 |
|---|---|---|---|
| **ゲシュタルト：近接** | 近いものは同じグループと知覚される | 関連要素の間隔 < 無関係な要素の間隔 を常に守る | 余白スケールを段階化（例：4/8/16/24/32/48）。「要素内 < 要素間 < セクション間」の使い分けルール |
| **ゲシュタルト：類同** | 見た目が同じものは同じ機能と知覚される | 同じ機能は同じ見た目、違う機能は違う見た目にする | ボタンの種類（primary/secondary/danger）を厳格に定義。リンクの見た目を統一 |
| **ゲシュタルト：共通領域** | 枠や背景で囲まれたものはまとまりに見える | カード・パネルの境界を意味のあるまとまりにだけ使う | カード・セクションの使用基準。「枠の入れ子は 2 段まで」など |
| **ゲシュタルト：整列・連続** | 揃っているものは関連して見え、秩序を感じる | グリッドに乗せる。揃えの基準線を減らす | グリッド（12 カラム等）、テキストの左揃えを基本にするルール |
| **視覚的階層** | サイズ・太さ・色・位置で重要度が伝わる | 1 画面の最重要要素を 1 つに決め、それを最も目立たせる | タイポグラフィスケール（見出しレベルの数を限定）、強調手段の優先順 |
| **前注意属性** | 色・大きさ・向き・動きは意識する前（約 0.2 秒）に知覚される | 強調色は意味のあるものにだけ使う。同時に目立たせるのは 1〜2 箇所 | 意味色トークン（success/warning/danger/info）を装飾に使うことを禁止 |
| **フォン・レストルフ効果** | 周囲と違うものが記憶・注目される | 目立たせたいものは「周囲と違う」ことで目立たせる。全部を目立たせない | CTA ボタンは 1 画面 1 つだけ primary |
| **認知負荷 / チャンク化** | 作業記憶の容量は小さい（一般に 4±1 のまとまり程度とされる） | 情報を意味のまとまりに分割する。覚えさせずに見せる | フォームのセクション分割、長い数字の区切り表示ルール |
| **フィッツの法則** | 目標が遠く・小さいほど操作に時間がかかる | よく使う操作は大きく・近くに置く。危険な操作は離す | クリック領域の最小サイズ、主要ボタンの配置位置、破壊的操作との距離 |
| **ヒックの法則** | 選択肢が多いほど判断が遅くなる | 同時に見せる選択肢を減らす。よく使うものを先に | メニュー項目数の上限、段階的開示のルール |

#### L2: ユーザビリティ原則（型によって強弱）

| セオリー | 何に作用するか | 採用すると守ること | DS への反映例 |
|---|---|---|---|
| **ニールセンの 10 ヒューリスティクス** | 使いやすさの総合チェックリスト（状態の可視化 / 現実との一致 / ユーザーの主導権 / 一貫性 / エラー防止 / 想起より認識 / 柔軟性と効率 / 美しく最小限 / エラーからの回復 / ヘルプ） | 評価基準として全画面のレビューに使う | レビュー用チェックリストとして設計書に添付 |
| **ヤコブの法則** | ユーザーは他のサービスで覚えた作法を期待する | ナビ・検索・ユーザーメニューなどは慣習通りに置く。独自性は中身で出す | 共通レイアウト（ヘッダー・サイドバー）の固定、アイコンの意味の標準化 |
| **一貫性と標準** | 同じことは同じ方法でできると学習が転移する | 用語・操作・配置を全画面で揃える | 用語集、操作パターン集（保存・削除・キャンセルの位置） |
| **想起より認識** | 覚えさせるより見せる方が負担が小さい | 選択肢・履歴・現在の状態を画面に出す | パンくず、選択中フィルターのチップ表示、最近使った項目 |
| **段階的開示** | 最初は必要最低限、詳細は求めに応じて見せる | 高度な設定・詳細情報は一段奥に置く | 「詳細設定」の折りたたみ、ドロワー、ドリルダウン |
| **柔軟性と効率** | 熟練者は近道を求める | ショートカット、一括操作、表示のカスタマイズを用意する | キーボードショートカット一覧、一括選択、列の表示切替 |
| **エラー防止と回復** | 失敗を起こさせない・起きても戻れる | 破壊的操作には確認か取り消しを用意する。入力はその場で検証する | 確認ダイアログ vs Undo の使い分けルール、インラインバリデーション仕様 |
| **ドハティの閾値** | 応答が約 400ms を超えると操作のリズムが崩れる | 即応答できないときは状態を見せる | ローディング・スケルトン・楽観的更新の使い分けルール |
| **テスラーの法則（複雑さ保存）** | 複雑さは消せず、誰かが引き受ける | 複雑さをユーザーではなくシステム側で吸収する | 賢いデフォルト値、自動入力 |
| **美的ユーザビリティ効果** | 美しい UI は使いやすいと感じられ、多少の問題が許容される | 見た目の品質を一定以上に保つ（ただし装飾で情報を邪魔しない） | ビジュアルスタイルのガイド |

#### L3: 視線とレイアウト（型によって選ぶ。法則ではなく「観察された傾向」）

| セオリー | 何に作用するか | 採用すると守ること | 向いている型 |
|---|---|---|---|
| **F パターン** | 文字や一覧が多い画面では、上部を横に読み、左端を縦に流し読みする | 重要情報は左上。各行の先頭（左端）に識別しやすい語を置く。ラベルは左揃え | A, D, 一覧画面全般 |
| **Z パターン** | 情報が少なく視覚的な画面では、左上→右上→左下→右下と流れる | 右下（視線の終点）に CTA を置く | F, E のシンプルな画面 |
| **レイヤーケーキ** | 見出しだけを拾い読みする | 見出しを具体的に書き、見出しだけで内容が分かるようにする | 設定画面、ドキュメント、C |
| **逆ピラミッド（要約→詳細）** | 上ほど重要・要約、下ほど詳細 | 上段に結論（KPI・ステータス）、下段に明細 | B, C, ダッシュボード全般 |
| **グリッドシステム** | 配置の秩序と、画面間の一貫性を作る | 全画面で同じカラム・ガターを使う | 全型 |

注意：頻繁に使うアプリ（A, B）ではユーザーが配置を覚えるので、**初見の視線誘導よりも「画面間で配置と意味が変わらないこと」の方が効く**。

#### L4: 情報設計とデータ可視化（データを扱う画面があれば強く効く）

| セオリー | 何に作用するか | 採用すると守ること | DS への反映例 |
|---|---|---|---|
| **Shneiderman のマントラ**（Overview first, zoom and filter, then details on demand） | 情報探索の順序 | 最初は全体像、次に絞り込み、詳細は要求されたときに見せる | ダッシュボードの 3 段構成テンプレート、ドリルダウン導線 |
| **Tufte の Data-ink 比** | グラフで「データ以外のインク」が多いほど読みにくい | 3D・濃いグリッド・不要な枠・影・凡例の重複を削る | チャートの標準スタイル（グリッドは薄く、軸は最小限） |
| **Stephen Few のダッシュボード原則** | ダッシュボードは一目で状況把握するためのもの | 1 画面に収める。比較対象（目標・前期）を並べて示す。装飾で注意を散らさない | KPI カードに「現在値・比較値・差分」を必須項目にする |
| **Cleveland & McGill の知覚精度** | 人が値を正確に比べやすい表現には順位がある（位置 > 長さ > 角度 > 面積 > 色の濃さ） | 正確な比較が必要なら棒・折れ線。円グラフや面積は構成比の大まかな把握だけに | 使ってよいチャート種別と用途の対応表 |
| **データインクの色分け** | 色の使い方で意味が変わる | カテゴリは色相、量は明度（連続色）、正負は発散色で表す | カテゴリ色・連続色・発散色のパレットを別々に定義 |
| **情報アーキテクチャ（IA）** | 情報の分類・ラベル・ナビゲーション | ユーザーの言葉でラベルを付け、階層を浅く保つ | ナビ構造、画面一覧、用語集 |

#### L5: 規格・ガイドライン（採用したら従う）

| セオリー | 何に作用するか | 採用すると守ること | 採用度の目安 |
|---|---|---|---|
| **WCAG 2.2 レベル AA** | アクセシビリティの国際規格 | 本文の文字コントラスト 4.5:1 以上（大きな文字は 3:1）、UI 部品やグラフ要素のコントラスト 3:1 以上、色だけで情報を伝えない、キーボードで操作できる、フォーカスが見える、クリック領域は最小 24×24 CSS px | 原則「必須」。社内限定ツールでも AA 相当を推奨 |
| **参照するデザインシステム**（Material Design / Apple HIG / Microsoft Fluent / 利用中の UI ライブラリの思想） | 部品の振る舞いや状態の定義を借りられる | 1 つを「母艦」に決め、迷ったらそれに従う。混ぜない | UI ライブラリを使うなら、その思想を母艦にするのが自然 |

### 型別の推奨（Step 2 の推奨回答の出発点）

| 型 | 特に「重視」にするもの | 弱めてよいもの |
|---|---|---|
| A. 業務オペレーション | 柔軟性と効率、一貫性、フィッツ、F パターン、エラー防止 | 段階的開示のしすぎ、大きな余白、美的効果の優先 |
| B. モニタリング | 前注意属性、フォン・レストルフ、逆ピラミッド、Few、ドハティ | 装飾、平常時の情報の主張 |
| C. 意思決定・レポート | 視覚的階層、逆ピラミッド、Shneiderman、Cleveland & McGill、レイヤーケーキ | 操作の多さ、情報密度 |
| D. 探索・分析 | Shneiderman、想起より認識（選択中の条件表示）、柔軟性と効率 | 固定レイアウト、過度な単純化 |
| E. 一般ユーザー向け | ヤコブ、ヒック、段階的開示、エラー防止と回復、テスラー | 情報密度、ショートカット |
| F. 集客・訴求 | Z パターン、視覚的階層、フォン・レストルフ、美的効果 | 情報密度、柔軟性と効率 |

Step 2 の合意内容は次の形で見せる。

```markdown
### 採用セオリー
| レイヤー | セオリー | 採用度 | このアプリでの作用（1行） |
|---|---|---|---|
```

## Step 3: デザイン原則の策定

### 3-1. 衝突の洗い出し

採用したセオリー同士がぶつかる箇所を Claude が洗い出して提示する。**原則はこの衝突の解決から生まれる。** 衝突がない部分はセオリーをそのまま守ればよく、原則にする必要は薄い。

よく起きる衝突：

| 衝突 | A に寄せると | B に寄せると | 判断の材料 |
|---|---|---|---|
| 情報密度 ⇔ 認知負荷の低減 | 一覧性が高く、画面遷移が減る | 初見でも迷わない | 利用頻度と熟練度（高いほど密度寄り） |
| 段階的開示 ⇔ 想起より認識 | 画面がすっきりする | 必要な情報をすぐ見られる | その情報を使う頻度 |
| 一貫性（ヤコブ）⇔ 独自性・ブランド | 学習コストが低い | 印象に残る | 型が E・F か、A・B か |
| 美的効果 ⇔ Data-ink 比 | 魅力的に見える | データが読みやすい | データを読むことが主目的か |
| フィッツ（大きな操作領域）⇔ 情報密度 | 操作しやすい | 1 画面に多く載る | 入力デバイス（タッチの有無） |
| エラー防止（確認）⇔ 効率 | 誤操作が減る | 操作が速い | 失敗のコストと、取り消せるか |
| 柔軟性（カスタマイズ）⇔ 一貫性 | 各自が最適化できる | サポート・教育がしやすい | ユーザー数と役割の多様さ |

各衝突について、Step 1 の回答を根拠に **推奨の寄せ方** を示し、ユーザーに決めてもらう。

### 3-2. 原則の言語化

決めた寄せ方を、5〜7 個のデザイン原則として書く。各原則は次の形式にする。

```markdown
#### 原則N：<短い一文。何を優先するかが分かる言い方>
- 優先するもの / 抑えるもの：
- 根拠：（Step 1 のユーザー像）＋（採用したセオリー）
- Do：<この原則に沿った具体的な判断の例>
- Don't：<この原則に反する具体的な判断の例>
```

### 3-3. 原則の品質チェック

書いた原則を Claude が次の観点で点検し、問題があれば書き直しを提案する。

- **何かを捨てているか**：「使いやすく」「シンプルに」のように誰も反対しない文は判断に使えない。選ばなかった側が読み取れる文にする
- **迷ったときに判断できるか**：レビューで「この原則ならAとBのどちらか」を決められる粒度か
- **このアプリ固有か**：別のアプリにそのまま貼っても通用するなら、ユーザー像との結び付きが弱い
- **数は 5〜7 個か**：多すぎると覚えられない。セオリーの言い換えにすぎない原則は削る
- **原則同士が矛盾していないか**：矛盾するなら優先順位を付ける（原則に番号順の優先度を持たせてもよい）

良い例と悪い例（ユーザーへの説明に使う）：

- 悪い例：「ユーザーにとって分かりやすい UI にする」→ 何も捨てていない
- 良い例：「熟練者の速度を初見の分かりやすさより優先する。ただし破壊的操作だけは初見基準で守る」→ 捨てたもの（初見の分かりやすさ）と例外が明確

## Step 4: デザインシステムへの落とし込み

原則とセオリーを、実装できる具体的なルールに変換する。**すべてのルールに「どの原則・セオリーから来たか」を書く**（後で「なぜこの値なのか」を説明できるようにするため）。

ここで決めた内容は Step 6 で 3 つのファイルに振り分ける。トークンの値は `design-tokens.json` に、使用禁止事項とコンポーネントの必須ルールは `.claude/rules/design.md` に、その理由は `design-foundation.md` に入る。決める段階では振り分けを意識せず、チャット上で一つずつ合意を取ればよい。

トークンには **2 層の名前** を付ける。

- **基本トークン**（primitive）：色や数値そのもの。例：`color.red.600`、`space.4`
- **意味トークン**（semantic）：用途を表す名前で、基本トークンを参照する。例：`color.status.danger` → `{color.red.600}`

コンポーネントや画面からは **意味トークンだけを使う** ルールにする。こうすると「赤は異常のみ」のような原則をトークンの名前で強制でき、色を変えるときも 1 箇所で済む。

既存の UI ライブラリやテーマ設定がある場合は、ゼロから作らずに「既存の値を原則に照らして評価し、変更が必要な箇所だけ決める」進め方にする。

### 4-1. デザイントークン

次の順で決める（上ほど原則の影響が大きい）。各項目で推奨値を提示し、根拠を添える。

1. **色**
   - 意味色（success / warning / danger / info）：用途を限定し、装飾への使用を禁止する
   - 中立色（背景・面・境界線・文字の階調）
   - ブランド色（ここはビジュアルスタイル＝好みで決めてよい部分）
   - データ可視化用パレット（L4 を採用した場合：カテゴリ色・連続色・発散色）
   - すべての文字色 × 背景色の組み合わせでコントラスト比を確認する（WCAG を採用した場合）
2. **余白**：段階化したスケール（例：4px 基準）と、「要素内・要素間・セクション間」の使い分けルール（近接の原則）
3. **タイポグラフィ**：サイズスケールと見出しレベルの数、行間、数字の等幅表示（表や KPI がある場合）
4. **サイズ**：クリック領域の最小値（フィッツ、WCAG）、行の高さ（情報密度の原則に合わせて通常 / コンパクト）
5. **角丸・影・境界線**：ビジュアルスタイル。ただし「影や枠でまとまりを示すか」は共通領域の原則に従う
6. **モーション**：時間とイージング。状態変化を伝える目的に限定する

### 4-2. コンポーネント仕様

アプリで使う主要コンポーネントを挙げ、それぞれに原則から来る仕様を書く。すべてを網羅しなくてよい。**原則が効いてくるコンポーネントだけ**を対象にする。

例：
- ボタン：種類（primary は 1 画面 1 つ）、破壊的操作の見た目と配置
- テーブル：密度の切替、列の固定、数値の右揃え、並べ替えとフィルターの状態表示
- フォーム：ラベルの位置、必須表示、バリデーションのタイミングとメッセージ
- KPI カード：必須項目（現在値・比較値・差分・期間）
- 通知・アラート：重要度ごとの表示方法と、消えるかどうか
- 空状態・ローディング・エラー状態：すべての主要コンポーネントで定義する

### 4-3. 使用禁止事項

原則とセオリーを破りやすい典型的なパターンを「やってはいけないこと」として明文化する。禁止事項はレビューで最も使われるので、具体的に書く。

例：
- 意味色（赤・黄・緑）を装飾やブランド表現に使わない
- 色だけで状態を区別しない（アイコンかテキストを併用する）
- 1 画面に primary ボタンを 2 つ以上置かない
- グラフに 3D 表現を使わない
- 余白スケールにない値を使わない

### 4-4. トレーサビリティ表

最後に、原則とルールの対応を表にまとめる。

```markdown
| 原則 / セオリー | トークン | コンポーネント | 禁止事項 |
|---|---|---|---|
```

## Step 5: レイアウトと検証方法

### 5-1. 共通レイアウト（アプリの骨格）

- グリッド（カラム数、ガター、最大幅、ブレークポイント）
- ナビゲーションの位置と構造（ヤコブの法則に沿って慣習的な位置に）
- ヘッダー・サイドバー・コンテンツ領域の役割分担

### 5-2. 画面テンプレート

アプリに登場する画面の種類ごとに、配置の型を決める。各テンプレートで「どの原則・視線パターンに従うか」を明記する。

- 一覧画面：F パターン。上部に検索・フィルター・主要アクション、左端に識別子列
- 詳細画面：レイヤーケーキ。見出しでセクションを区切る
- フォーム：1 カラム、ラベル上置き、セクション分割（チャンク化）
- ダッシュボード：逆ピラミッド＋Shneiderman。上段 KPI → 中段トレンド → 下段明細
- 設定画面：段階的開示。よく使う設定を上に

テンプレートはテキストの配置図（ASCII で十分）で示す。

ここで決めるのは **型** まで。アプリに具体的にどんな画面があり、どう遷移するかは `grill-screen` で要件定義書と組み合わせて決める。ユーザーが具体的な画面の話を始めたら、「それは画面設計の段階で決めます。ここでは全画面に共通する型を決めましょう」と引き戻す。

### 5-3. 検証方法

原則が機能しているかを確かめる方法を決めて設計書に残す。

- **5 秒テスト**：画面を 5 秒見せて隠し「一番重要な情報は何でしたか？」と聞く。原則で最重要とした要素が答えられれば階層設計は機能している
- **タスクテスト**：Step 1 の主要タスクをそのまま課題にし、迷わず完了できるかを見る
- **ヒューリスティック評価**：ニールセンの 10 項目で各画面をチェックする
- **アクセシビリティ確認**：コントラスト比のチェック、キーボード操作、色覚シミュレーション
- **原則レビュー**：新しい画面や変更を、デザイン原則と禁止事項に照らしてレビューする

## Step 6: 3 つのファイルの出力

### 6-1. サマリの提示と合意

まず `design-foundation.md` の内容をチャット内に提示して合意を取る。合意が取れてから 3 つのファイルを書き出す。提示・保存する直前の文体は、プラグインルートの `shared/japanese-style.md` に従う（grill 系スキル共通）。

### 6-2. 保存先の確認

デフォルトの保存先は次の通り。書き出す前に一覧で見せ、「このパスで保存してよいですか？」と確認する。

- `docs/design-foundation.md`
- `design-tokens.json`（リポジトリ直下。`src/styles/` などトークン置き場の慣習があればそちらを推奨する）
- `.claude/rules/design.md`

既に同名ファイルがあれば、内容を読んだうえで上書き・統合・別名のどれにするか確認する。特に `.claude/rules/` に既存のルールがある場合は、重複や矛盾がないかを確認してから書く。

### 6-3. 3 つのファイルを書く

各ファイルの雛形と書き方のルールは `references/output-templates.md` に従う。要点は次の通り。

- `docs/design-foundation.md`：「なぜそうするか」を残す。トークンは名前・用途・根拠だけを書き、値は書かない
- `design-tokens.json`：W3C Design Tokens（DTCG）形式。意味トークンの `$description` に用途と根拠の原則番号を書く。WCAG を採用した場合は、書き出し前に文字色 × 背景色のコントラスト比をスクリプトで計算する
- `.claude/rules/design.md`：ルールに ID（`DS-01` など）と根拠の原則番号を振り、判定できる命令形で短く書く


### 6-4. 書き出し後の確認

3 つのファイルを書き出したら、次を確認してユーザーに報告する。

- `design-tokens.json` が JSON として正しく読み込めること（実際にパースして確認する）
- 設計書のトークン名と `design-tokens.json` のトークン名が一致していること
- `.claude/rules/design.md` の各ルールに根拠の原則番号があり、その原則が設計書に存在すること
- コントラスト比の確認結果（WCAG を採用した場合）

## Step 7: 次のステップの選択

保存後、次の選択肢を提示する。勝手に次の作業を始めない。

- **コードに起こす**：`design-tokens.json` から CSS 変数・Tailwind 設定・UI ライブラリのテーマ設定を生成する。既存のスタイル定義があれば置き換えの影響範囲を先に示す。トークンの正本は JSON のまま保ち、生成したファイルには「design-tokens.json から生成」と明記する
- **Figma に起こす**：Figma の MCP が使える場合、`design-tokens.json` を Figma Variables（Collection とモード）として登録し、主要コンポーネントを作る。Figma 側のスキル（`figma-generate-library` など）があれば先に読み込む。値を Figma で変えた場合は JSON にも反映する運用を決めておく
- **画面設計に進む**：`grill-screen` で、要件定義書と本設計書をもとに画面一覧・画面遷移・各画面のワイヤーフレームを作る。`grill-screen` が無い間は、`grill-me` で技術設計と合わせて画面一覧と遷移を決める
- **ここで終える**

個人や少人数で Claude Code を中心に開発する場合は、「コードに起こす → 画面設計」の順を推奨する。デザイナーや関係者と見た目を合意してから作る場合は、「Figma に起こす → 画面設計」を推奨する。

## 重要な原則

### 解説してから決めてもらう

ユーザーがセオリーの作用を理解しないまま「推奨でいいです」と進むと、原則が自分の言葉にならない。各レイヤーで最低限「このセオリーはこう効く、あなたのアプリではこうなる」を示してから採用度を聞く。ただし解説は短く、具体例中心にする。講義にしない。

### 1 回に 1 レイヤー・1 論点

情報量が多いスキルなので、一度に出しすぎない。Step 2 は 1 レイヤーずつ、Step 3 は 1 衝突ずつ進める。関連性が高いものはまとめてよい。

### 推奨回答と理由を必ず添える

「どうしますか？」と丸投げしない。Step 1 のユーザー像を根拠にした推奨を必ず添える。ユーザーが反対したら理由を聞き、文脈を更新して進める。

### 見た目の好みとセオリーの判断を混ぜない

ユーザーが「こっちの方が見た目が好き」と言ったら、それがビジュアルスタイルの話か、使いやすさの話かを切り分ける。ビジュアルスタイルなら尊重する。使いやすさに影響するなら、セオリーを根拠に影響を説明したうえでユーザーに判断してもらう。

### Step 1 を判断軸に粘る

以降のすべての推奨は Step 1 のユーザー像から導く。Step 1 と矛盾する決定が出てきたら「Step 1 では〇〇と決めましたが、この決定はそれと合わないように見えます」と指摘する。

### コードを読めば分かることは聞かない

既存のスタイル定義や UI ライブラリはまず調べる。決め直す必要があるのは、原則に照らして問題がある箇所だけ。

### 値の正本は 1 つにする

トークンの値は `design-tokens.json` だけに書く。設計書・ルール・コード・Figma に同じ値を手で書き写すと、必ずどこかでずれる。設計書とルールはトークン名で参照し、コードと Figma は JSON から生成・同期する。

### 具体的な画面は決めない

本スキルの範囲は全画面に共通する土台まで。具体的な画面構成や遷移の話が出たら `grill-screen` に回す。土台と個別画面を同時に決めると、個別の事情に引っ張られて原則が歪む。

### スコープに合った深さで

個人開発の小さなアプリと、複数チームで使う業務システムでは必要な深さが違う。小規模なら原則は 3〜5 個、コンポーネント仕様は主要なものだけで十分。すべてを埋めることより、原則が決まっていることの方が大事。

### 完璧を目指さない

決めきれない論点は推奨値で仮決めし、「未確定事項」に理由付きで残す。実際に画面を作り、検証してから見直す方が健全。

### 図を使う場合

画面テンプレートの配置図やトレーサビリティを図で示すときは、プラグインルートの

## 成果物の保存提案

Step 6 で 3 つのファイルを書き出したら、Vault への保存を AskUserQuestion で提案する（選択肢は
「保存する / 保存しない」）。手順と原則はプラグインルートの `shared/vault-save-hook.md` に従う。

保存するのは `docs/design-foundation.md` だけでよい。`design-tokens.json` と
`.claude/rules/design.md` はリポジトリで使うためのファイルなので Vault には置かない。
種別は「設計書」として渡す。**プロジェクト名が分かっていれば本文と一緒に `vault-save` へ渡す**。分からなければ
`vault-save` が聞く。
