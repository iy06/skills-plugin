# grill-loop

自律・並列のエージェント開発を「どう回し続けるか」を、質問駆動で上流から確定し、ループ設計書と起動物として出力して合意を取るためのスキル。

## このスキルの位置づけ

- `grill-product` → アプリの **要件定義書** を作る（何を作るか）
- `grill-me` → 実装前の **設計書** を作る（どう作るか）
- `grill-you` → 既存対象を **理解** する（コード / 概念）
- `grill-loop` ← **本スキル**：それらを **どう回し続けるか** を設計する（運用の設計）

`grill-product` / `grill-me` が「1 つの成果物をどう作るか」を扱うのに対し、`grill-loop` は「複数の成果物を継続的に、なるべく無人で消化し続ける仕組み」を扱う。両者で設計が固まった直後に続けて使うのが典型。

### 責務の境界：設計するが、常駐しない

**ループを実際に回す実体は `/goal`・`/loop`・routine・シェルスクリプトであって、このスキルではない。** grill-loop の責務は、それらを正しく配線するための **設計書** と、そのまま動かせる **起動物**（ラベル定義・起票雛形・consumer スクリプト・routine prompt・緊急停止手順）を生成し、人間の合意を取るところまで。生成が終われば grill-loop の出番は終わり、以降は生成物が回す。この境界を混同して「grill-loop が常駐してループを管理し続ける」設計にしないこと。

## このスキルの目的

「issue を自動で消化させたい」「並列でエージェント開発を回したい」といった漠然とした願望を、事故らない運用に落とすこと。無人ループは、設計を詰めずに走らせると「際限なく動いて予算を溶かす」「勝手にマージして壊す」「同じブランチを複数エージェントが取り合う」といった事故を起こしやすい。本スキルは、上流から順に運用の論点を潰し、**止まる条件・マージの条件・競合の防ぎ方が明記されたループ設計書**に合意してから起動物を出す。

ゴールは `grill-me` と同じく「grill されることで、ユーザー自身が自分の運用要件を言語化できる」状態を作ること。したがって Claude は各論点に**推奨回答と根拠**を添え、選択肢形式で判断を引き出す。

## 前提：すべては「完了条件付き work item」に正規化する

このスキルが設計するループは、入力を **「完了条件付きの work item」= GitHub issue** に正規化してから回す。トリガーが何であれ（人間の起票、CI 失敗、定例タスク）、まず issue の形に落としてキューに入れる。これがループの唯一の入り口。

### issue の要件

- **ラベル**：状態と扱いをラベルで表す
  - `loop:ready`（着手可）/ `loop:wip`（作業中）
  - `merge:auto`（自動マージ許可）/ `merge:manual`（人間マージ必須）
- **本文**：背景 ／ 設計書（リンクか貼付）／ **grill-me 形式の完了条件ブロック**（機械検証できる形で）

### 2 つのレーン

- **feature レーン**：`grill-product` / `grill-me` の成果を issue 化する。**本スキルが起票コマンドを出力**する（Step 8）。完了条件は人間が設計書から書く＝質を人間が担保できる。
- **fix レーン**：CI 失敗などから自動起票される issue。完了条件は定型（「再現テストを追加 → pass → 既存テストも green」）。producer（自動起票）インフラが要る分、feature レーンより後回しでよい。

## 全体フロー（grill-me と同型）

1. **対象の確認**（何を回したいか。呼び出し時に添えられていれば飛ばす）
2. **現状調査**（既存ラベル・GitHub Actions・issue クエリ・worktree 運用を調べる）
3. **論点の洗い出しと依存関係の整理**
4. **上流から順に質問**（各論点に推奨回答と根拠を添える・選択肢形式）
5. **論点が決まるごとに、ループ設計書の該当セクションを提示して合意**
6. **出し切ったらサマリを出し、追加論点をユーザーに促す**
7. **ループ設計書の提示**
8. **「起動物を生成しますか？」の確認**し、Yes なら起動物一式を出力

## Step 1: 対象の確認

`/grill-loop` だけで呼ばれた場合、「何を回し続けたいですか？」と確認する。`grill-product` / `grill-me` から続けて呼ばれた場合は、その成果物（要件定義書 / 設計書）を対象の出発点にする。

## Step 2: 現状調査

質問を始める前に、ループを配線する先のリポジトリと運用を調べる。`grill-me` の「コードを読めば分かることは聞かない」と同じ原則で、調べれば分かることは質問しない。

### 調査範囲の目安

- **既存ラベル**：`gh label list`。ループ用ラベル（`loop:*` / `merge:*`）が既にあるか、命名がぶつからないか
- **GitHub Actions**：`.github/workflows/`。既存の CI / レビュー Action、required checks、`concurrency` 設定
- **issue の運用**：現在どんなラベル・クエリで issue が管理されているか（`gh issue list`）。誰が起票しているか
- **worktree 運用**：`git worktree list`、既存の worktree 運用スクリプトや命名規約
- **実行基盤の制約**：ROS・社内ネットワーク・実機など、実行場所を縛る要因があるか（README / インフラ設定から読み取る）

調査結果から「既に決まっていること」と「ユーザーに聞かないと決められないこと」を仕分け、質問は後者に絞る。

## Step 3: 論点の洗い出しと依存関係の整理

頭の中で運用の論点ツリーを作る。上流（対象キュー・レーン）が決まらないと下流（マージポリシー・並列度）が決められない、という依存を意識し、上流から質問する。論点ツリーを毎回見せる必要はないが、Claude 内部では常に持つ。

## Step 4: 上流から順に grill する論点

以下の 9 論点を、**上流から順に**、各論点に推奨回答と根拠を添え、選択肢形式で確認する。設計影響の小さい枝は推奨回答で流してよい（grill の本質は設計影響度に応じた徹底さであって、全てを等しく厳しく問うことではない）。

### 1. 対象キュー（最上流）

何を消化するのか。**issue クエリ（ラベル / 担当で絞る）** か **checklist ファイル（リポジトリ内 md の未チェック行）** か。そして**そのキューの所有者は誰か**。

- 推奨：issue クエリ。理由：状態遷移をラベルで表せ、並列時の排他（`wip` 付与）や停止判定（`ready` 数）を `gh` で機械的に扱える。checklist は所有と粒度が曖昧になりやすい。
- ここで決めた「所有者」が、以降「リストは人間が所有する」原則の主語になる。

### 2. レーン

**feature / fix のどちらから配線するか**。

- 推奨：**feature 先行**。理由：producer（自動起票）インフラが不要で即日動き、完了条件の質を人間（起票者）が担保できる。fix レーンは自動起票の仕組みを足してから追加すればよい。

### 3. 駆動と実行場所

**いつ起動するか** × **どこで動かすか**。

- 駆動：毎朝 schedule（cron / routine）／ issue opened（Actions）／ セッション内タイマー（`/loop`）
- 実行場所：ローカル worktree ／ クラウド routine ／ 自前サーバ
- 推奨：**ROS・社内ネットワーク・実機が要るならローカル worktree か自前サーバ**（クラウドからは届かないため）。**GitHub 完結（コードと `gh` だけで閉じる）なら routine を推奨**（基盤管理が要らず毎朝動く）。駆動は「毎朝 schedule」を既定にすると全体停止判定（論点 5）と噛み合う。

### 4. 1 反復の定義

ループ 1 周で何をやるか。

- 原則：**issue 1 件 = worktree 1 本 = セッション 1 本 = `/goal` 1 個**。
- 完了条件は **grill-me の完了条件セクションを流用**する（issue 本文の完了条件ブロック＝`/goal` に渡すゴール）。機械検証できる形であること（「重要な原則」参照）。

### 5. 停止の二層

止め方を **個別** と **全体** の二層で決める。ここを抜くと「上限のない無人ループ」になり最も危険。

- **個別停止**（1 反復の終わり）：`/goal` の達成条件 + ターン上限 + `timeout`。3 つのうちどれかに必ず掛かるようにする。
- **全体停止**（その日はもう起動しない）：キュー状態で判定。例「`loop:ready` の P1 が 0 かつ checklist が全行 done」。
- 推奨：**全体判定は朝の起動時に行い、満たされていれば consumer を起動しない**。走り出してから止めるより、走らせないほうが安全。

### 6. マージポリシー

PR をどう扱うか。

- 既定：**`merge:manual`（人間がマージ）**。
- `merge:auto` を許すのは、**次を全て満たす**ときだけ、と条件を明記する：
  - required checks が green
  - レビュー Action の MUST 指摘が 0
  - 変更パスが許可 glob（例 `docs/**`, `test/**`）の内側
  - `gh pr merge --auto` を使う（checks 通過後に GitHub 側でマージ）
- **新機能・スキーマ変更・公開 API は `merge:manual` 固定**。推奨：初期は全部 manual で回し、事故らない範囲が見えてから auto の glob を広げる。

### 7. 並列度と予算

どれだけ同時に、いくらまで回すか。

- 同時 worktree 数（推奨：**初期 2〜3**。競合と予算が見えてから増やす）
- 日次起動上限（1 日に消化する issue 数の上限）
- issue ごとの `timeout`（1 反復の壁時計上限）
- `/usage` を確認する頻度（予算監視）
- 推奨：小さく始めて、競合・予算・マージ事故が出ないことを確認してから広げる。

### 8. 競合ガード

並列で壊さないための排他。**書き手は 1 ブランチ 1 人**が大原則。

- issue に `loop:wip` を付けて取得＝排他（同じ issue を 2 エージェントが取らない）
- fixer レーンは mutex ラベルで 1 本に絞る
- 直近コミットが bot なら今回はスキップ（bot 同士の往復ループを防ぐ）
- Actions 側は `concurrency` で同一対象の多重起動を止める
- **緊急停止**：stop ファイル（例 `.loop-stop`）か特定ラベルを、**全ループが冒頭でチェック**し、あれば自主停止する

### 9. エスカレーション

自動で解けないときの人間への渡し方。

- 同一の指摘に **2 巡対応しても解消しなければ人間へ**（無限リトライを防ぐ）
- 断念レポートの形式（何を試して何で詰まったか）
- 通知先（Slack チャンネル等）

## Step 5: 決まるごとにセクションを提示

大きな論点が決まったら、その決定を反映したループ設計書の該当セクション（ドラフト）を簡潔に見せ、「この方向で合っていますか？」と確認する。設計書全体ではなく、今決まった部分だけのスナップショット。

## Step 6: サマリと追加論点の確認

出し切ったと感じたら、決定事項をサマリで提示して問う：

> 「ここまでで運用ループの設計に必要な論点は出せたと思います。他に詰めておきたい点はありますか？（例：リポジトリ固有の制約、通知の粒度、失敗時の巻き戻し）」

追加が出れば答え、なければ Step 7 へ。

## Step 7: ループ設計書の提示

以下の形でチャット内に提示する。複数のループ（feature / fix）を回すなら表を複数行にする。該当しないセクションは省略してよい。

```markdown
# <対象> ループ設計書

## ループ一覧

| ループ | 対象 | 駆動 | 1 反復 | 停止（個別 / 全体） | 実行場所 | マージ | 予算 |
|---|---|---|---|---|---|---|---|
| feature | `loop:ready` の issue | 毎朝 schedule | issue 1 = worktree 1 = /goal 1 | 個別: goal+ターン上限+timeout / 全体: ready(P1)=0 | ローカル worktree | 既定 manual、glob 内は auto | 同時 3 本 / 日次 5 件 / 20 分 |

## 競合ガード
- 書き手は 1 ブランチ 1 人（`loop:wip` で排他）
-（論点 8 の決定を列挙：mutex / bot スキップ / concurrency など）

## エスカレーション
-（論点 9 の決定を列挙：2 巡ルール / 断念レポート形式 / 通知先）

## 緊急停止手順
-（stop ファイル / ラベルの名前と、全ループが冒頭でどうチェックするか）

## 備考
- 未確定事項、今後 fix レーンを足すときの TODO など
```

設計影響の小さいループなら表 1 行で完結することもある。テンプレートに縛られず規模に合わせる。

### 図を使う場合：HTML ファイルを書き出してプレビュー

ループの状態遷移（`ready → wip → PR → merged`）などを図で示すときは、プラグインルートの
`shared/diagram-preview.md` の手順に従う（grill 系スキル共通）。

## Step 8: 起動物の生成

設計書に合意できたら、次で確認する：

> 「この設計で起動物を生成しますか？」

Yes なら、`references/artifacts.md` の雛形を使って以下を生成する。**Step 4 の決定を反映**し、
設計書で決めた並列数・timeout・全体停止条件・マージ条件・許可 glob を必ず穴埋めすること。
既存で足りているもの（例：Step 2 で見つかった既存ラベル）は再生成しない。

| # | 生成物 | 生成する条件 |
|---|---|---|
| 8-1 | ラベル定義コマンド一式 | 既存ラベルで足りなければ |
| 8-2 | feature レーンの起票コマンド雛形 | feature レーンを使うなら |
| 8-3 | consumer スクリプト | 論点 3 で自前駆動を選んだなら |
| 8-4 | routine の prompt 文面 | 論点 3 で routine を選んだなら |
| 8-5 | 緊急停止手順の README 断片 | 常に |

生成後、**「この起動物は grill-loop の出力です。ここから先はこの生成物（と `/goal`・`/loop`・routine）が回します」**と、責務が生成物へ移ったことを明示する。

## 重要な原則（grill-me と同じ節立て）

### リストは人間が所有し、ループはそれを消化する

ループがやるのは「人間が承認したリストの消化」だけ。**仕事を自己生成する producer（勝手に issue を作り続ける仕組み）を作らない**。何をやるかの判断は、人間がキュー（issue / checklist）に載せる形で握る。これを破ると、ループが自分で仕事を増やし、際限なく走り続ける。

### 機械検証できない要件は完了条件に入れない

`/goal` は完了を機械的に判定できて初めて止まれる。「いい感じにする」「使いやすくする」は完了条件にならない。テストの pass、コマンドの exit 0、ファイルの存在など、**pass / fail が自動で付く形**だけを完了条件に入れる。曖昧な要件は `grill-me` / `grill-product` 側で完了条件に翻訳してからキューに載せる。

### 1 ブランチに書き手は 1 人

並列で最も壊れやすいのが、同じブランチ / 同じ issue を複数エージェントが触ること。`loop:wip` による排他、worktree の分離、fixer の mutex で、**あるブランチを書き換えるのは常に 1 エージェント**を保証する。

### 上限のない無人ループを作らない

個別停止（goal + ターン上限 + timeout）と全体停止（キュー状態）の二層を必ず入れる。予算上限・日次上限・並列上限も明示する。**「気づいたら一晩中回って予算を溶かしていた」を構造的に防ぐ**のがこのスキルの主目的の一つ。上限が 1 つでも欠けていたら設計書に戻る。

### 推奨回答を必ず添える（grill 族共通）

「どうしますか？」という丸投げはしない。各論点に Claude の推奨と根拠（現状調査 / 一般的なベストプラクティス）を添える。運用は判断材料が多いほど決めやすく、対話のテンポも保てる。ユーザーが反対すれば理由を軽く聞き、文脈を更新して進める。

### 完璧を目指さない（grill 族共通）

すべての運用リスクを潰そうとすると設計が終わらない。feature レーンだけ・並列 2 本・全部 manual マージ、から小さく始め、回しながら広げる方が健全。未確定は設計書の「備考」に正直に残す。

### grill するのは運用設計であってユーザーではない（grill 族共通）

詰めるのは運用の安全性であって、ユーザーを問い詰めることではない。推奨回答と選択肢形式で対話を軽やかに保つ。

## 下流 / 関連

- 生成した consumer スクリプト・routine を実際に回すのは `/goal`（1 反復の完了判定）・`/loop`（インターバル実行）・routine（クラウド定期実行）。grill-loop はそれらの入力を作るだけで、常駐しない。
- 完了条件の質はループの安全性を直接左右する。曖昧なら `grill-me` に戻り、完了条件を機械検証できる形に翻訳してから issue 化する。
