# vault-save

成果物を Obsidian Vault に保存する。**「どこに置くか」の判断をこのスキルに集約する**のが役割で、
呼び出し側は Vault のパスもフォルダ名も持たない。利用者ごとに Vault の構成は違うので、
パスを各スキルに散らすとプラグインとして配布できなくなる。

## 呼ばれ方

- grill 系スキルの「成果物の保存提案」から、本文と種別を渡されて呼ばれる
- ユーザーが直接「これを Vault に保存して」と言って呼ぶ

どちらでも手順は同じ。渡されていない情報（種別、プロジェクト名）は聞く。

## Step 1: 設定を読む

`~/.claude/vaults.json` を読む。形は次の通り。

```json
{
  "default": "<既定の vault キー>",
  "vaults": {
    "<キー>": {
      "path": "<Vault のルート>",
      "label": "<表示名>",
      "scope": "<何を置く場所か>",
      "git": false,
      "explicit_only": false
    }
  }
}
```

**設定が無い、または読めない場合は、勝手にパスを決めない。** ユーザーに保存先を聞き、
「今後のために `~/.claude/vaults.json` を作りますか」と提案する。設定が無いのに推測でどこかへ
書くと、利用者が把握していない場所にファイルが増える。

## Step 2: Vault を決める

- **既定は `default` が指す Vault。** ユーザーが何も言わなければここに置き、いちいち聞かない
- **`explicit_only: true` の Vault は、ユーザーが明示指定したときか、こちらから確認して承認が
  取れたときだけ。** 共有 Vault は他人が読む場所で、個人の下書きが混ざるとチームがそこを
  信用しなくなる。「共有側に置きますか」と聞くのは、内容が明らかにチーム向けのときに限る

`git: true` の Vault に書いたときは、**コミットも push もしない。** ファイルを置いたことと、
そこが git リポジトリであることを伝えて、コミットの判断はユーザーに渡す。共有リポジトリへの
反映は本人のタイミングで決まる。

## Step 3: フォルダを決める

成果物の種別からフォルダを決める。

| 種別 | フォルダ | 補足 |
|---|---|---|
| 要件定義書 / PRD | `01-Projects/<プロジェクト名>/` | プロジェクト名が渡されていなければ聞く |
| 設計書 | `01-Projects/<プロジェクト名>/` | 同じプロジェクトの要件定義書と並べる |
| 決定事項 / ADR | `Decisions/` | プロジェクトを横断して引くため、プロジェクト配下に埋めない |
| コード理解 / 調査メモ | `03-Resources/` | 対象のリポジトリ名でサブフォルダを切ってよい |
| 上記以外 | ユーザーに聞く | 推測で新しい階層を作らない |

**フォルダが無ければ作る。** Vault は育つ前提の入れ物で、既定の階層が最初から揃っているとは
限らない。ただし表に無い種別で新しいトップレベルのフォルダを作るのは、聞いてから。

## Step 4: ファイル名を決める

`YYYY-MM-DD-<内容が分かる短いスラッグ>.md`。日付は推測せず `date +%F` で取る。

- スラッグは日本語のままでよい。Obsidian はファイル名でリンクを解決するので、読める方が引きやすい
- **同名のファイルが既にあれば上書きしない。** 中身を読み、更新なのか別物なのかをユーザーに聞く

## Step 5: 書き出して報告する

先頭に frontmatter を付ける。Obsidian 側で後から絞り込めるようにするため。

```yaml
---
created: YYYY-MM-DD
type: <種別>
source: <呼び出し元のスキル名 / 手動>
tags: []
---
```

書き終えたら、**Vault の label・フォルダ・ファイル名**を 1 行で報告する。フルパスの読み上げは
要らない。

## 原則

### 判断をここに集約する

「どこに置くか」の知識をこのスキルの外に漏らさない。呼び出し側が `01-Projects/` のような具体的な
フォルダ名を持ち始めたら、それは設計が壊れている合図。パスが変わったとき直す場所は常にここ。

### 保存は合意の後に来る

呼び出し側はユーザーに確認してからこのスキルを呼ぶ（`shared/vault-save-hook.md`）。呼ばれた
時点で保存の合意は取れているが、Vault の選択やファイル名の衝突で迷ったら改めて聞いてよい。

### 成果物は作らない

渡された本文を整えて保存するだけで、内容を書き足したり要約したりしない。文体を整える必要が
あるなら、それは呼び出し元が `shared/japanese-style.md` に沿ってやること。ここで手を入れると、
ユーザーが合意した内容と保存された内容がずれる。
